## 2f. WP6 notes (reservations and locks)
- Granting is only `ReservationService.acquire` (one `BEGIN IMMEDIATE` via `locks/txn.immediate`, all-or-nothing, replaces the task's previous set). The HTTP API deliberately has no "reserve" route: `Admission.reserve` does conflict check + acquire + READY -> RESERVED in one place. The scheduler (WP7) must call `Admission.release(task_id)` in a `finally` when a run ends or fails to start (Nirandyr rule 27); the lease (default 120 s, max 3600) is only the safety net.
- Keys: `normalize.normalize_scope(project_root, raw)` is the only way a path becomes a key (validated, symlink/junction-resolved, lower-case, `/`, `.meta` stripped, 8.3 names refused). Directory scopes end in `/` and overlap everything below; a file and a same-named directory overlap. Per project for `path`/`git_branch`, machine-wide for `unity_editor`, `gpu`, `blender`, `device:<serial>`, `build`, `test_env`, `custom`. Change `normalize.canonical` and every stored key is stale (no migration rewrites keys; old rows expire with their lease).
- Heavy: any request whose type is in the profile's `heavy_resources` (default `unity_editor, gpu, blender, device`) also takes the implicit `class:heavy` exclusive, so max 1 heavy task (Q8) holds even if the scheduler is wrong. The scheduler still limits heavy admission and decides priority/yielding (WP7).
- Leases: holders renew with `heartbeat(task_id)`; a lapsed lease is deleted only if `liveness(task_id)` is false. The callback (`supervisor.live_run_for_task`) is asked BEFORE the write lock (it takes the supervisor lock; asking inside the transaction could deadlock). WP7 should call `heartbeat` from its tick for every RESERVED/RUNNING task and `sweep` at startup/recovery (WP9).
- External locks never write: `LockFile`/`LockDir` (existence only, contents never read or echoed), `JobBoard` (tolerant fail-closed Markdown parser, 1 MB cap, rows owned by "cpm" ignored: WP11 writes those, see 2j), `DevLock` (lists `~/.device-locks`, never blocks; lanes must wrap device commands with `devlock.wrap_command`). No managed-repo script is executed by CPM. Profile fields: `lock_files` (name -> file), `lock_dirs` (name -> folder with `*.lock`).
- Desktop claims block exclusive path requests only (reading is allowed). Adding a claim never stops a worker; the response lists `affected_tasks` already holding an overlapping path.
- External edits (scenario 7): `ExternalWatcher.scan` snapshots HEAD + `git status` entries (size, mtime) via hardened `gitinfo._git` and stores it in `settings`; it reports reserved paths touched by a change (events `external.modification`, `external.conflict`). Polling git replaces a filesystem watcher (no dependency). The scheduler must call it periodically; WP10 must call it right before integration. A HEAD move without a file list marks the whole tree changed.
- Migration `0003` adds `reservations.project_id/label`, unique `(task_id, resource_type, resource_key)` and table `desktop_claims`. Backup/restore (WP9) covers the new table. If WP8 also lands a `0003`, renumber the later one (`down_revision`).
- Not touched on purpose: `workers/supervisor.py` (WP7 wires reservations around `start`), `tasks/service.py` (scope entries stay plain paths; lane resources are passed as `extra`).

## 2g. WP7 notes (scheduler)
- One deterministic `Scheduler.tick()` (serialised by a lock; a second concurrent call returns `errors=["another tick is running"]`). Order inside a tick: housekeeping (heartbeat RESERVED/RUNNING reservations; release reservations of tasks no longer RESERVED/RUNNING; put a RESERVED task without a worker back to READY; `ExternalWatcher.scan` per project with a worker every `external_scan_s`; promote BLOCKED tasks whose dependencies are done, only when `block_reason` starts with "waiting for tasks", never a hand-blocked task; auto-retry) then, unless paused, dispatch.
- Queue order (`policy.order_key`): `priority` (low first), then for heavy tasks the smaller `estimate_microusd` (a longer job yields, Nirandyr rule 27), then task id. A task that cannot start is skipped, lower ones still get a chance (no head-of-line blocking).
- Limits: global = wizard `max_parallel_agents` (1..8, supervisor re-checks), optional `per_project_limit`, `heavy_limit` fixed at 1 (Q8; the `class:heavy` exclusive in `locks/` enforces the same). "In flight" = RESERVED/RUNNING tasks the supervisor reports `busy`; a RUNNING task without a worker is an orphan left to WP9.
- Start path: `Admission.reserve(task, extra=resources_for(task))` -> `RunSupervisor.start(...)`, which does the budget admission (WP8) itself. Any `RunError` (live runs off, no key, per-run ceiling, `BudgetRefused`, ...) or other exception from `start` = deferral: reservations released in a `finally`, task back to READY, one `scheduler.deferred` event per distinct reason, per-task backoff 30/60/120/300 s (in memory). Nothing a refusal says can fail a task. API tasks get `max_budget_microusd = min(estimate, CPM_LIVE_RUN_MAX_MICROUSD)` (the ceiling when no estimate); nothing is spent unless the existing live gates pass.
- Timeouts: `hang_timeout_s` / `max_runtime_s` from `scheduler.config` are passed to every run (supervisor kills and marks FAILED). Retries: FAILED -> READY by the scheduler only for billing modes in `retry_billing_modes` (default `["mock"]`: retrying an API task spends again, opt in via `PUT /api/scheduler/config`), at most `max_auto_retries` (default 2, counts manual retries too via `retry_count`), after `retry_delay_s`, and never when the last `identical_failure_limit` (2) runs failed with the same fingerprint (run status + reason with digits blanked). Giving up writes one `scheduler.gave_up` event; the task stays FAILED for a person.
- Never started by the scheduler: PAUSED, PAUSED_BUDGET (a person decides), BLOCKED by hand. COMPLETED is never set here.
- Loop: `CPM_SCHEDULER=1` starts `run_forever` in the app lifespan (default off, so tests and `python -m cpm.main` stay inert; `scripts/start.ps1` turns it on). `POST /api/scheduler/tick` runs the same pass once. `pause` stops dispatch only (housekeeping continues); it is persisted in `settings`.
- Hooks for later packages: `resources_for(task)` (WP12 lanes return `ResourceRequest`s such as `gpu`/`unity_editor`, which makes the task heavy), `start_args_for(task)` (scenario for mock runs, lane limits). WP10 owns reservations from TESTING on: the scheduler releases them when a task leaves RESERVED/RUNNING; the gate must `Admission.reserve`-style re-acquire if it needs paths during review.
- No schema change (no migration; v0.11.0 follows 0004; 0005 stays free).
- Known gaps: `POST /api/tasks/{id}/runs` (manual start) still bypasses reservations, by design a person's explicit action (R-WP7-1); cooldowns are in memory and reset on restart; the voice "restart when GPU free" rule (rule 49) comes with WP13 as a `resources_for` + lowest priority.

## 2h. WP9 notes (recovery, v0.12.0)
- Startup order in `api/app` lifespan: backup of the existing DB (never blocks startup) -> `upgrade` -> `Recovery.reconcile()` -> scheduler start. Recovery starts nothing; a second `reconcile()` changes nothing (tested).
- A run with status STARTING/RUNNING that the supervisor does not hold is an orphan: run -> CRASHED, budget hold released, reservations released, task RUNNING -> FAILED (or PAUSED when the run log ends inside a non-idempotent step), RESERVED -> READY. A RUNNING/RESERVED task with no run row is handled the same way.
- Non-idempotent steps: `permissions.non_idempotent_step` (today `git add|commit`) -> the permission event carries `step`, the supervisor writes `step_begin` and closes it with `step_end` at the next permission/text/result/stopped/error/session event. The same rule applies on the live path: a worker killed or crashed inside a step PAUSES the task instead of FAILED, so the scheduler cannot retry a half-done commit. Add new tools to this list when a lane introduces one (WP12+).
- Worktrees are only reported (`recovery.last_report.worktrees`), never deleted. Dirty or unmerged ones say so.
- Backups: `sqlite3` backup API (WAL safe), verified with `integrity_check`, newest 10 kept in `data/backups/`. Restore is `python -m cpm.recovery restore FILE` with CPM stopped; the replaced DB is kept as `cpm.db.before-restore-<stamp>`.
- Gaps: TESTING/REVIEWING/CORRECTING tasks have no worker yet (WP10 must define their restart rule); the Windows leftover-process kill relies on the Job Object (KILL_ON_JOB_CLOSE) and is untested on the PC; the step list is conservative (false "half done" costs one click, a miss costs a repeated commit).

## 2i. WP10 notes (gate, diff review, pull request, v0.13.0)
- Flow: worker run ends -> task TESTING -> `GateService.run` (clicked, or `auto_run_pending` on an unpaused scheduler tick; a task is re-judged only when it changed since its last result) -> checks in this order: criteria exist -> something changed -> no unexpected file -> project tests -> clean merge onto the base (`git merge-tree --write-tree` on a dangling probe commit) -> independent review. Outcomes: `passed` (COMPLETED, evidence `{acceptance_gate: passed, tree, by}`), correction (CORRECTING, then a new run of the same task with the findings as inert JSON feedback; the run moves it CORRECTING -> RUNNING -> TESTING), `failed` (FAILED), `waiting` (stays TESTING: `criteria_missing`, `needs_trust`, `conflict`, `review_pending`, `error`).
- Bounds: `gate.max_corrections` (default 2, max 5) and an early stop when the same failure fingerprint (digits ignored) repeats right after a correction. A correction that cannot start (parallel limit, budget, worktree) PAUSES the task and says why.
- Consumers: `GET /api/tasks/{id}/{review,changes,diff}`, `POST /api/tasks/{id}/{gate,gate/approve,integrate}`, `GET/PUT /api/gate/config`, `GET/PUT/DELETE /api/credentials/github`, `TickReport.gated`. `app.js`: `reviewPane` (task page), `integrationBox`, `gitView` (queue + GitHub token + gate settings). A renamed summary key (`tests`, `unexpected`, `review`, `conflicts`, `feedback`, `gave_up`, `correction`) breaks `gateSummary`; `tests/ui/e2e.mjs` step 6f is the check.
- Status table changes (tests/unit/test_task_states.py): REVIEWING -> TESTING (restart recovery re-asks the gate) and CORRECTING -> RUNNING (the correction worker).
- `INTEGRATED` means "pull request opened"; the merge is the person's click on GitHub and CPM does not watch for it (a closed-unmerged PR leaves the task INTEGRATED; limitation).
- Reviewer: only `MockReviewer` ships. Mock tasks use it; API tasks get `review_pending` until a live reviewer (cheap model, no tools, diff-only) is plugged into `ReviewerSource.live`, which needs Micah's go for its budget. A person can approve `review_pending` results after reading the diff (`gate/approve`: latest result only, tree unchanged).
- Restart recovery: REVIEWING -> TESTING, CORRECTING -> PAUSED (a CORRECTING task never has a worker); TESTING is left alone because the gate is idempotent.
- Known gaps (not bugs): the correction run is not re-admitted through reservations, so a Desktop claim made after the first run is not checked until the gate's own merge/scope checks; the merge check uses the base as last fetched (CPM never fetches), GitHub reports a newer conflict on the PR; a task that legitimately changes nothing ends FAILED (`no_changes`); tests are skipped, not failed, when no test command is known (shown as "skipped" in the gate result and the PR text).

## 2j. WP11 notes (job board writer, v0.14.0)
- Flow (explicit clicks only; nothing claims by itself): `POST /api/tasks/{id}/job-board/claim` reads `docs/JOB_BOARD.md` at the local `origin/<default>` commit, `boardwriter.add_claim` appends ONE row (`| CPM #<id>: <title> | cpm | \`paths\` | claimed | <date> |`, columns filled by header name), `gitops.commit_blob` builds a commit on the base with a temporary index (no checkout, no ref, main tree untouched), `push_branch(source=sha)` pushes `claude/cpm-claim-task-<id>`, then one docs-only PR is opened (rule 40 text sections). `.../release` does the same with `release_claim` (status -> `released`, row kept as history); it needs a claim PR that was merged (the row must exist on the base board). `GET .../job-board` shows both PRs and whether the base board shows the row (`none|claimed|released`).
- Fail closed: no table with files + status + job columns -> refuse; non-UTF-8 -> refuse; > 1 MB -> refuse; overlap with another owner's active row (same rule-13 parser the scheduler uses) -> refuse; no declared scope -> refuse; scope paths with `|`, backtick or control characters -> refuse; titles are stripped of the same. CRLF/LF of the file is kept (diff is one added line). Task ids match exactly (`CPM #7:` never matches `#70`).
- Consumers: the scheduler's `JobBoard` adapter already ignores `cpm`-owned rows, so CPM's own claim never blocks CPM; other threads see it as soon as the PR is merged. A renamed header detection (`jobboard._FILES_HEADERS`) changes what the writer accepts as well.
- Steps persisted (`committed -> pushed -> pr_open`, unique per task and action); a retry resumes and never pushes twice. The base is the local `origin/<default>` as last fetched (CPM never fetches); a stale base shows up as a conflict on GitHub. A project without `origin/main` refuses.
- Unverified (needs the PC): the real `docs/JOB_BOARD.md` column names and layout (WP6 open item). If the real file is not a table with these columns the writer refuses instead of guessing; adjust `_tables` then. Real GitHub PR creation is untested like WP10's.
- Not done on purpose: claims are not made or released automatically on task start / INTEGRATED (that would be an outward action without a click; revisit once Micah wants it).
## 2j. WP12 notes (lane framework, v0.15.0)
- A lane is an entry of `lanes:` in the project's profile (`lanes/spec.py` is the schema; strict, `yaml.safe_load`). A task opts in with `tasks.lane` (must name a lane the profile defines; validated on create/edit; locked while the task is active). No lane = every code path behaves as before (tested).
- Enforcement points, all outside the worker's control: (1) `workers/permissions._decide_bash` asks `ToolContext.bash_extra` (built from the lane's `commands` by `lanes/commands.make_hook`, rebuilt in the child from `RunSpec.lane`) BEFORE the built-in allowlist, after the shell-operator filter; (2) `RunSupervisor.start` resolves the lane and runs `preflight` (required tools/paths exist) before any budget is held: failure is a `RunRefused`, i.e. a scheduler deferral with backoff; (3) the scheduler asks `LaneService.resources` (heavy types make the task heavy: max 1 heavy task, `BUILD_RUNNING.lock` and the other external locks apply as for any heavy task) and `start_args` (`limits.max_runtime_s`, `hang_timeout_s`); (4) the gate's lane step.
- Gate order: unexpected files (the generic 5 MB rule yields to the lane's `max_file_bytes` for files under the lane's asset paths) -> **lane step** -> project tests -> merge check -> reviewer. Lane step = artifact policy (location, extension, size, binary policy `ask|lfs_only|deny`; `lfs_only` reads the root `.gitattributes`, never follows a symlink) + validators (registered kinds; unknown kind or a crash = error, fail closed; `Unavailable` = wait) + report sections of the worker's last `result` event. Errors -> correction with the findings as feedback (bounded like other corrections); `ask` binaries or unavailable validators -> `lane_waiting` (task stays TESTING; a person approves or fixes); lane removed from the profile -> `lane_error` (wait, never pass).
- Extension API for WP13/14: `lanes.registry.register_validator(kind, fn)` (fn(ValidationContext, params) -> list[Finding]; read-only; may raise `Unavailable`), plus profile entries. Validators must not run heavy tools: those run as worker commands under the lane's resources; validators judge their output files.
- Command rules cannot name a shell, network tool, deletion tool or `git` (`FORBIDDEN_PROGRAMS`), and an interpreter (python, node, ...) only with a fixed script in `prefix` and no flags/positionals. Paths in `path`/`out_path`/positional args are checked textually and against the real filesystem (symlink/junction); `out_path` must also be inside the lane's asset paths and not protected. `needs_trust` rules run only in a trusted workspace.
- Not built (on purpose): no lane screen in the UI (the task page shows no lane yet; WP15 follow-up), no `devlock` wrapping of device commands (lanes needing devices must put the wrapper in their fixed command; a first-class adapter comes with the first device lane), no check that `required_tools` are really the tools the command names resolve to on PATH (the Bash tool resolves names; keep the tool dir first in the worker's safe PATH when WP13/14 land), validators for audio (WP13); 3D/map/Unity validators are WP14 (2k).
- Migration `0007` adds `tasks.lane` (after WP11's `0006`). If another package also lands a `0007`, renumber the later one (`down_revision`); `tests/integration/test_health_and_db.py` pins the head revision.

## 2f. WP8 notes (budget)
- Single money path: a worker never states what it cost. The child emits tokens, `RunSupervisor._record_usage` prices them from the `prices` table through `BudgetLedger.record_usage` (one row per SDK message id, `price_version` stored). Only scripted `mock` runs may pass an explicit `cost_microusd` (that is how the burst scenarios work).
- Admission is part of `RunSupervisor.start` (before the worktree, the state change and the spawn): `BudgetLedger.admit` runs in `BEGIN IMMEDIATE`, checks month (global), project (per month), task (whole life) and the optional manual credit balance, and inserts a `budget_reservations` row. Exposure = spent + sum(max(0, hold - spent by that run)), so a run's hold and its own spend are never counted twice. The hold is released in `_finish_rows` (every end path), or by `admit`'s caller on any exception before the run exists.
- API runs always need a hold; mock runs only when the caller passes a cap and a monthly budget exists. With no wizard cap `admit` refuses (`no_cap`).
- Task ceiling without a configured task budget: API tasks fall back to `CPM_LIVE_RUN_MAX_MICROUSD` (WP5 audit rule "all runs of a task share one ceiling" now lives in the ledger; the old check in `_live_gates` was removed).
- Caps: `wizard.config` values, overridden by `budgets` rows (`scope` month/project/task, `scope_ref` period/id). `POST /api/budget/top-up` and the `add_budget` option raise a row; nothing raises a cap silently. Thresholds (70/90/100 %) emit one `budget.threshold` event per level and cap value; a raised cap starts a new series.
- `PAUSED_BUDGET` is now resumable with the SDK session (like PAUSED). The five options live in `POST /api/tasks/{id}/budget-action`; resuming goes through the normal start, so it is admitted again against cumulative task spend.
- Not built (by decision, see DECISIONS 2026-10-26): daily budget level, cost-center UI (data API only; WP15), automatic Console reconciliation (manual `POST /api/budget/reconcile`), the "request a checkpoint" message to a running worker at 90 % (the alert is logged in the run log with `checkpoint_requested`; WP10 sends it).
- Changing a price: `PUT /api/budget/prices/{model}` appends a version. Do not edit `prices` rows by hand; old usage rows keep the version they were priced with.
