# Rules for every Claude session working on this game

Micah's standing rules (2026-10-08). Read this before changing anything.

1. Before a feature: read `docs/plans/00_DECISIONS_MICAH.md` (his answers, they win), the module plan in `docs/plans/`, and `docs/plans/99_IMPACT_MAP.md` (what the change touches and the known risks).
2. With every build or plan change, in the same build:
   - update `docs/plans/99_IMPACT_MAP.md`: the matrix, the chains of consequences, the open risks, and a change-log line with the date and version;
   - update `docs/GAME_SYSTEMS.md` (what is built and its cascade), `docs/GAME_DEVLOG.md` (what shipped) and the in-game Help.
3. When a change creates or raises a risk, tell Micah in one line in the thread.
4. New saved keys go into `RealmCloud.Keys`. Old saves are repaired on load.
5. Version numbers go up in small steps (0.2.19, 0.2.20, ...). Only one thread builds the game at a time.
6. The idea library is `docs/library/` (pick by ID). New ideas from Micah go into a plan module or the library index.
7. The new-player tutorial (`Assets/Game/V2/Scripts/UI/RealmTutorial.cs`, decision 34) is updated with every feature a new player meets: add or change its tip in the same build, and keep Skip on every tip.
8. Readable text (Micah 2026-10-10): button labels never shrink below 75% of their size. Check the "[Realm] text audit" lines of a capture run (labels that do not fit, or would not fit 35% longer in German) and make those buttons bigger before shipping.
9. Security (Micah 2026-10-10): "Always check security issues in every new implementation, possible modifications, cheats, impersonating, etc." Every build checks its change for cheat and tamper risks (edited saves or stats on the phone, a modded APK, a spoofed save server, posing as another player in friends or groups) and writes the findings and what was done in the build's `docs/GAME_SYSTEMS.md` entry and the impact map risks. Before any production release, run a deep full security check (Micah 2026-10-10).
10. Integration test menu (Micah 2026-10-10, decision 68): integration builds have a menu giving access to every spell, school of magic, ability, feature, attribute and economy value (gold, items). Every build that adds a feature adds it to this menu in the same build. The menu is compiled out of production builds.
11. Verification program (Micah 2026-10-10, decision 66): after any major change that could shift chances or generated values (forge, sliders, rarity odds, loot, damage, economy), re-run `tools/sim/` (uniqueness and cost, then the combat and economy simulators when they exist) and record the numbers in the devlog. Run again before production with real player numbers.
12. Separate threads (Micah 2026-10-10): "Always run the tests in a separate thread unless told otherwise" and "Separate the tasks coding, test, audit, other in separate threads." The build thread codes and builds only. Phone tests and security audits each run in their own thread, started by the coordinator: the build thread sends the scope (APK, devices, commands, what to compare against; for audits, the security-relevant changes listed in the build notes).
13. Job board (Micah 2026-10-11): threads never edit the same files at once. Before a job, list the files it will modify and check `docs/JOB_BOARD.md` (re-read it just before every write). A file claimed by another active job is off limits: wait, work around it, or send your patch to the owning thread. Claim your files before the first edit and release them (status `done`) when the job ends. The build thread alone bumps versions, builds, uploads and commits.
14. Coordinator inbox (Micah 2026-10-10, decisions 83 and 157; read automatically at the start of every thread, and again before each build in a long thread): Micah's idea chat writes new ideas and answers to `docs/COORDINATOR_INBOX.md`. At the start of every thread, read the `NEW` rows and their linked decisions and plans, set each status (READ, PLANNED, DONE with version, QUESTION) and write results and questions for Micah under "Answers for Micah". Never delete a row.
15. Never pay-to-win (Micah 2026-10-10, decision 107): anything sold for real money only changes the look of the game (effects, character and mob skins). No power, no XP boosts, no gear, no gold.
16. Everything on screen can be turned off (Micah 2026-10-10, decision 105): every message, tip, notification, reminder or start-up screen gets an on/off switch in Settings in the same build.
17. Bug exploits (Micah 2026-10-10, decision 144): every build checks its change for gameplay exploits (duplication, infinite farming, rewards counted twice, kills counted from unreachable spots, escaping fights, skipping costs) and writes the findings next to the security findings of rule 9.
18. Money always visible (Micah 2026-10-10, decision 179): every window where something can be bought or paid (merchants, trainers, spells, forge, ascension, market, repairs, everything) shows the player's gold and any other cost currency in the same place, same style, always. New windows get it in the same build.
19. Phone tests (Micah 2026-10-11): the "Phone tests" thread runs every phone test. Handoff: for each new APK the build thread adds a row to `docs/tests/TEST_QUEUE.md` (version, APK path and SHA-256, what changed, what to test) and sends the phone test thread a cross-session message. The phone test thread tests the oldest untested row, fills its result columns and links the report (`docs/tests/TEST_<version>.md`). It sends "tests started" when it takes the phones (the build thread pauses Android builds and Unity's adb) and "tests done" with the bugs to fix when the phones are free. Only the phone test thread asks Micah for the phones.
20. Legal (Micah 2026-10-11, decision 202): any feature that touches personal data, money, user content, AI-generated content, licences or names updates `docs/legal/LEGAL_REVIEW.md` in the same job, and important points are told to Micah in one line.
21. Fastest test first (Micah 2026-10-11, decision 238): pick the test mode by what changed: automated Edit Mode tests and `tools/sim/` for calculations (levels, damage, loot, economy); Play Mode in the editor or a small test scene for logic and UI; an APK only for rendering, touch and performance. Before a version is called done, the APK run re-checks everything that was validated in simulation or Play Mode, plus a global APK test (rule 19). Record which mode tested what in the devlog.
22. Offline solo, online for anything shared (Micah 2026-10-11, decisions 239 and 241): a hero is created online once; solo play works offline and syncs later; selling, trading, gifts, the market, clans, world bosses and groups need a connection, and the server re-checks every item and value before it enters anything shared.
23. Calculations and data (Micah 2026-10-11, decision 253): simulators may run on the game VPS during development; every script lives in `tools/sim/` and Git; databases, saves and player data never go into Git (sync them to the PC instead); stop heavy calculations on the game server once real players use it.
24. Devices (Micah 2026-10-11): before any adb install, launch, tap, screenshot or Unity Build And Run on an emulator or a phone, take the device with `python tools/devices/devlock.py run --device <serial or any-emulator> --who "<thread>" --job "<what>" --prio <1-4> -- <command>` (or `acquire`, `heartbeat`, `release`). One holder per device; a free device goes to the most urgent waiting job (prio 1 urgent blocker, 2 phone round or release check, 3 normal test, 4 background), then the oldest; the coordinator may `bump` a job or `hold` a device. A lock not renewed expires by itself. Locks live in `%USERPROFILE%/.device-locks`, shared with the other projects on this PC, never in Git. Rule 19 still holds (phones only by the Phone tests thread); the lock replaces "pause Unity's adb". Details: `tools/devices/README.md`.
25. Builds and coders (Micah 2026-10-13 14:37, decision 372, replaces the 2026-10-11 "Build A / Build B" rule): only the Builds thread compiles release APKs, bumps versions, tags, uploads and merges release branches, in the build worktree D:\projects\game-build. The coordinator decides what is compiled and when (Micah: "tu gères ce qui doit être compilé et quand") and sends the Builds thread a pin: an audited commit with nothing unaudited before it (decision 347 cadence). Coder threads never wait for a build: they own the files they claim on the job board (rule 13), commit audited work to main (rule 30) and go on with the next job. One job is at most about 4 h with one owner (split bigger rows first). A version is a batch of audited changes with one APK and one phone round; only a prio 1 blocker ships alone.
26. Nothing heavy during a build (Micah 2026-10-13 11:54, decision 363: "Oui"): while `D:\projects\game-build\BUILD_RUNNING.lock` exists, no thread starts heavy PC work (Unity batch runs, `pc_check` compiles, Blender, local model runs, GPU jobs). Work already running pauses at its next safe point, frees its memory as decision 354 says (checkpoint, quit, `wsl --shutdown`) and resumes when the file is gone. The Builds thread writes the file from the moment a release build is ready to start (including its wait for free memory) until Unity exits; every other Unity run also writes it through `tools/gpu_lock.sh`, so Unity runs never overlap. Micah keeps the CIRL emulator and Android Studio closed when CIRL is not testing.
27. Resources (Micah 2026-10-13 11:59, decision 364): tests on emulators, phones and the PC are short. A job starts only when the resources it needs are free (RAM, GPU, device lock, build lock). It may try to free them, but never disturbs whoever uses them now. When it ends, even on failure, it releases everything and checks that it really is released (lock files gone, processes exited, RAM back, phone screen off). A device lock covers only the test actually running and is released between steps, so a build never waits hours on a lock held through idle time. Priority: short processes first; long generations (1 h or more: voice training, Blender batches, AI runs, sims) start only when performance allows, have the lowest priority and yield to anything shorter.
28. Tutorial rules (Micah 2026-10-13 12:08, decision 365; adds to rule 7): the tutorial is logical; each piece of information appears only once; when a window has to be closed the tip says so, and closing it (or doing the asked action) validates that page and moves on; each page appears at the right moment, tied to the action or information it explains. Every change to the tutorial is checked against these rules in the same build.
29. Waiting for Micah (Micah 2026-10-13 13:20, decision 366, every thread, always): whenever a thread waits for Micah (a decision, an answer, an action on his side such as phones, a setting or a root step), it also tells the coordinator at once what it waits for, so the coordinator shows him clearly that a step or an action is expected from him.
30. Commits in the shared tree (coordinator 2026-10-13, after three sweeps): never use the shared git index of D:\projects\game and never commit whole copies of files you did not change. Fetch; stop if HEAD != origin/main. Build a temporary index (GIT_INDEX_FILE) from HEAD with only your files, and for shared docs only your hunk applied to HEAD's version; commit with `git commit-tree`, move HEAD with a compare-and-swap `git update-ref HEAD <new> <old>` (redo if HEAD moved), push, then run `git reset -q <new> -- <every path of that commit>`, including the files it created (otherwise the shared index shows them as staged-deleted and a later careless commit deletes them). If the working copy holds other threads' pending hunks in a shared doc, also add your hunk there. Helper: `python tools/git/safe_commit.py -m "<msg>" --file <own file> --append <shared doc>=<block file> --content <path>=<prepared file>`.

## CLOUD FIRST, ALWAYS FREE (Micah 2026-10-15 18:15 UTC)
Micah: « Tout ce qui peut tourner dans le cloud y va … Uniquement des fils cloud Claude ou mes propres VPS, jamais un service payant. » « GPU se fait sur mon PC, à moins qu'un GPU gratuit soit à disposition. »
36. **Cloud first.** Code, reviews, audits, calculations, sims, analyses, scripts, plans and documents run in Claude cloud threads or on Micah's own VPS, never on a paid service. The PC is only for what needs it: Unity builds and compile checks, emulator and phone tests, GPU jobs (voice, images, story generation, training) unless a free GPU exists. On the PC rules 24, 26 and 27 still hold (locks, free RAM and GPU, release everything at the end).
37. **Cloud threads work by pull request.** Each cloud thread works on its own branch `claude/<role>-...` of `Xxobster/Nirandyr`, based on the latest `main`, and opens a PR to `main` for each job (the PR text lists the files changed, the security and exploit findings of rules 9 and 17, and what still needs the PC). Cloud threads never push to `main` directly. Rule 30 (`safe_commit.py`, shared index) applies to commits made on the PC, not to cloud branches. If the repo cannot be reached, the thread gives Micah the exact steps to grant the Claude GitHub app access.
38. **Merge gate.** Only the PC Compilation thread merges PRs. For each PR it compiles the game and runs the Edit Mode tests on the PR merged into the current `main` (a local merge, or GitHub's `refs/pull/<n>/merge`), and merges only when they pass AND the PR is audited (rule 39); if `main` has moved since that run, it runs them again on the new merge before merging. It merges with "Create a merge commit" only, never squash or rebase, so the audited commit hashes are the ones that land on `main`. Docs-only PRs (every changed file is under `docs/` or is a Markdown file outside `Assets/`) are outside the gate and are merged as soon as they arrive; anything else, `Packages/` and `ProjectSettings/` included, goes through the gate. Builds still alone bumps versions, builds and releases (rules 25, 33).
39. **Audit gate for PRs.** The Audit thread audits PR commits before merge and appends the usual machine lines `Audited: <hash8> ... (round N, PASS|FAIL)` to `docs/security/AUDIT_CLIENT_0.2.66.md` through its own docs-only PR, so `tools/release/queue_build.sh` reads them unchanged. A PR is audited when every commit in it that touches anything outside the docs-only paths of rule 38 has a PASS line on `main`. On a FAIL, Audit comments once on the PR with the findings; the owner pushes fixes to the same branch and the new commits are audited again. Every merge commit that lands on `main` and touches anything outside those docs-only paths gets its own Audited line in Audit's next scan of `main`: a clean merge after a `git show --remerge-diff` check, a merge that resolved conflicts after a full review. Until then integration builds only warn and production waits. `queue_build.sh` reads `Assets/` and `tools/` only; Builds adds `Packages/` and `ProjectSettings/` to its check, and until then Audit lists those commits in its round. Audit cannot compile in the cloud; the compile and Edit Mode tests are Compilation's merge check (rule 38), and the round says so.
40. **Job board from the cloud.** A cloud thread claims its files (rule 13) with its job-board row in a small docs-only PR opened before its first code edit; until it is merged, the files an open PR changes count as claimed, so every thread also checks the open PRs before editing. Anything a cloud thread cannot do itself (Unity, phone or emulator, GPU, VPS root, Micah's settings) becomes a job-board row naming the owner thread, with the note under `docs/plans/` (rule 34); the thread does not wait on it.
41. **Anti-token.** Cloud threads follow rules 31 to 35: results stay in the thread's own chat; the coordinator hears only about a blocker, a decision that belongs to Micah, or work for another thread; no "done" reports, no FYI relays, short messages.

## MMORPG SCALE, QUALITY FIRST (Micah 2026-10-16 11:21 and 11:43 UTC, decisions 412 and 413)
Micah: « This is gonna be a MMORPG, with thousands of players. So that has to be taken into consideration in every aspect of the game design. Donc comme doit tout être le plus random et unique possible (pour les histoires, les spells combinés, les maps, etc..), il faut qu'à chaque étape de création du jeu ceci soit pris en compte. »
42. **Thousands of players, one polished world.** Every plan, design step, feature and PR answers two questions in its text. **Scale:** does it hold with thousands of players at once (server CPU, storage and bandwidth per player, generation cost per player for AI text, voices and maps, queues, anti-cheat checks), and what does it cost per 1,000 players, within the free rule (36)? **Quality first** (decision 413, Micah 2026-10-16 11:43 UTC, « Tout commun », amending 412's uniqueness): the world map, the main story, side quests, dungeons, caves, villages and bosses are the same for every player, written, voiced (once, on the PC, at the highest quality) and tested once; generators and AI are authoring tools, never run per player. Randomness stays only where it costs no quality and no server time: loot, forge, combined spells, combat, the player's own choices. Revue checks both in every review. An accepted plan that clashes is listed for Micah with a recommendation (`docs/plans/412_scale_uniqueness_review.md`), never reworked unasked.

44. **Never idle.** When a task ends, the thread pulls `origin/main` and takes its next own row on the job board (`docs/JOB_BOARD.md`) at once. If it has none, it takes an unowned row that fits its role, or writes the next useful row for its role and does it. A thread stops only for a real blocker or a wait on Micah (rule 29 still applies: tell the coordinator what it waits for). A long job (a build, a sim, a GPU run) is watched with Monitor, and the thread chains the next step as soon as it ends instead of waiting for a message. Rules 25 to 27 still decide when heavy PC work may start.

## TEST YOUR CHANGE, FIX EVERYWHERE (Micah 2026-10-18 12:16 and 12:50 UTC, decision 443)
Micah: « Quand tu fais une modification, tu testes que ça fonctionne. » « Quand tu corriges un bug, tu vérifies que ce bug n'apparaît pas ailleurs, partout dans le jeu … il faut rester dans les limites du raisonnable … sois proactif. »
45. **The author tests the real outcome.** The thread that makes a change tests what the player will actually get, not only compile and uiaudit: tap each new card or button and check the result (for example each start spell card teaches its own spell). The brief and the PR text say how it was tested (rule 21 picks the mode).
46. **Fix the same bug everywhere.** After fixing a bug, the fixer searches for the same pattern wherever the same action exists (other buttons with the same action, other zones, other quest parts, other NPCs) and fixes those too, without being asked. Keep it targeted and reasonable: the same pattern, not a scan of the whole app. What was found and fixed goes in the PR text; what is too big becomes a job-board row (rule 34). Allowed in token-saving mode (decision 436).

## WEEKLY TOKENS (Micah 2026-10-21)

Below 15% left start nothing new and finish only safe steps (docs, tests, own branches; no deploy, merge, force, GPU or shared-file edits); at the reserve write the handoff (`docs/jobs/HANDOFF_<role>_<date>.md`) so Claude after the reset or another AI can continue without risk. Details: `docs/procedures/token_budget.md`. The Claude API from PowerShell works beside Claude only under `docs/procedures/api_parallel.md`, with Micah's go for the paid budget (rule 36).

## STANDING HABITS (moved here from the project instructions, Micah 2026-10-21)
51. **Ask, recommend, give exact steps.** If the task is unclear, you are unsure, or the change could break an existing feature, ask Micah (a decision card). Work may go on in your own branch on the recommended option, but nothing is merged, pinned or shipped before Micah answers when the change could break an existing feature or cannot be undone. Put open questions at the end of the answer, each with a recommendation. End every answer with recommended next steps, checked as rule 43 says. When Micah has to act, give the exact steps. Say at once when a new idea clashes with a principle or a decision, and what you recommend instead.
52. **Cannot do it? Write the ChatGPT prompt.** When a task cannot be done from the cloud (VPS or server access, a tool you lack), write a ready-to-paste prompt for ChatGPT in `docs/jobs/CHATGPT_<task>.md` (what to do, exact commands, how to check the result) and add the job-board row of rule 40.
53. **Document everything.** Every change and every decision is written down (rule 2 files, plan, devlog) so another AI can take over. Only Conception numbers decisions.
54. **Check the cascade.** Before adding or changing a feature, follow it through the impact map (rule 2). Example: a new spell school also touches the forge, the spellbook, the integration test menu (10), the icons list (47), the tutorial (7), Help, `tools/sim/` (11) and the save keys (4).
55. **Thread names** start with the role: "Codeur 2 : ...", "Audit : ...", "Tests : ...", "Compilation : ...", "Conception : ...", "IA : ...", "Art : ...", "Revue : ...", "Voix : ...".
56. **Model choice.** Sonnet 5.5 by default (coding, approved plans, UI, ordinary bugs, tests, docs, art/voice/VPS jobs). Opus 5.5 only for architecture, security audits (xhigh before production), a hard bug Sonnet failed twice, critical reviews, complex algorithms, high-risk multi-system plans. Opus writes a short plan, Sonnet builds it; do not switch back and forth or keep Opus for a whole workflow. Never lower the audit level when the quota is tight: a security audit stays Opus (xhigh before production).
57. **One task per thread, then hand off.** Never reuse a thread for another kind of work (an audit thread never does UI). When the task is done, verified and documented, write the handoff of rule 50, commit it and recommend a fresh thread. Never cut an unfinished task or drop open issues to save tokens.
58. **Time estimates** are made by Conception when it plans, in hours; anything over 4-5 h is flagged to Micah there. An accepted plan starts automatically, whatever its hours: never ask again at launch. Ask again only if the real cost is much larger or the plan changes.
59. **Urgent vs not urgent.** Important and urgent work runs on the PC (fast Unity compile and phone loop). Everything not urgent, however important, goes to the cloud (rule 36).
60. **PC offline.** Check `rc_session_status` first: often only the thread link dropped (`docs/process/PC_STAY_ONLINE.md`). If the PC is really offline, retry after 30 s, then 1, 2, 5, 10 and 20 min, then every 30 min, and resume the pending work as soon as it is back, without asking.
61. **Tests and threads (clarifies 12 with 45).** The author runs the fast tests of rule 21 (Edit Mode, sims, Play Mode) on their own change; phone/APK tests and security audits run in their own threads.
62. **Freeze after audit.** Owners never push to a branch once it is audited, until Compilation merges it. Exception: merging `main` into it to resolve conflicts, which is then re-audited.
